# 패키지 구조: 모상품 + 가상 출발일

관리자는 **모상품(product)** 과 **출발 규칙(rule)** 만 만든다. 출발일은 규칙에서 계산되는 **가상 값**이고,
DB의 `departure` 행은 아래 "저장 규칙"에 해당할 때만 생긴다.

## 1. 모델

```
product                   모상품: 이름, 박/일, 노선·시간, 일정(일차별), 선택관광·쇼핑·비고·조건, 기본 좌석 수, 상태(ACTIVE/INACTIVE)
 ├─ product_price         기본 가격: 대상 구분(성인/소아/유아…)별 판매가·유류할증료·제세공과금
 ├─ departure_rule        출발 규칙: 유효 기간(시작~종료) + 요일 집합
 │   └─ rule_exclusion    규칙에서 빼는 날짜
 └─ departure             (product, date) 단위 저장 행: 저장 규칙에 해당할 때만 생성
     └─ departure_price   날짜별 가격 덮어쓰기 (대상 구분별, 선택)
booking                   (product, date) 를 가리킨다
```

## 2. 출발일 집합 V(product)

```
V(p) = { d | 활성 규칙 r 이 있고  r.valid_from ≤ d ≤ r.valid_to
             그리고  weekday(d) ∈ r.weekdays
             그리고  d ∉ 제외일 }
       ∪ { d | departure(p, d) 행이 존재하고 (reserved_seats > 0 또는 pinned = true) }
```

- **예약이 있는 날짜는 규칙이 바뀌어도 V에 남는다.** (규칙을 줄여도 기존 예약이 사라지지 않는다)
- 과거 날짜는 목록·예약 대상에서 제외한다(출발일 > 오늘만).

## 3. 유효값(effective) 계산

| 값 | 규칙 |
|---|---|
| 좌석 정원 | 행이 있으면 `departure.capacity`, 없으면 `product.default_capacity` |
| 예약 좌석 | 행이 있으면 `reserved_seats`, 없으면 0 |
| 잔여 좌석 | `max(0, 정원 − 예약 좌석)` |
| 상태 | 행의 `status`(OPEN/CLOSED/CANCELED). 행이 없으면 OPEN. 잔여가 0이고 OPEN이면 **FULL(모객완료)** 로 파생 |
| 가격 | `departure_price` 덮어쓰기가 있으면 그 값, 없으면 `product_price` |
| 일정 날짜, TL | 출발일에서 계산 (저장하지 않음) |

## 4. 저장 규칙: `departure` 행이 만들어지는 때

| # | 시점 | 조건 | 결과 |
|---|---|---|---|
| **S1** | 첫 예약 | 날짜 ∈ V(p), 상품 ACTIVE, 출발일 > 오늘 | 예약 트랜잭션 안에서 행을 만들고 좌석을 확보 (`capacity` = 그 시점의 기본 정원 스냅샷) |
| **S2** | 관리자가 날짜에 직접 조치 | 마감/재개, 정원 변경, 가격 덮어쓰기, 출발 취소 | 행을 만들거나 갱신하고 `pinned = true` |
| **S3** | 관리자가 "출발일 추가" | 규칙 밖의 단일 날짜를 추가 | 행을 만들고 `pinned = true` (V에 포함됨) |

**만들지 않는 경우**
- **조회·검색·목록은 절대 행을 만들지 않는다.** (읽기는 부작용 없음, 계산만)
- V(p)에 없는 날짜의 예약은 거절한다(S3로 추가한 날짜는 예외).
- 비활성 상품, 과거 날짜는 만들지 않는다.

**동시성**
- 행 생성은 `PRIMARY KEY (product_code, departure_date)` 로 보장한다. 동시에 만들면 한쪽이 키 충돌 → 한 번 재시도해서 기존 행을 쓴다.
- 좌석 확보는 지금과 같은 조건부 UPDATE: `reserved_seats = reserved_seats + n WHERE reserved_seats + n <= capacity AND status = 'OPEN'`.
- `capacity`를 행에 스냅샷으로 두는 이유: 좌석 확보 UPDATE가 상품 테이블을 읽지 않아도 되고, 상품의 기본 정원을 나중에 바꿔도 이미 열린 날짜의 정원이 조용히 변하지 않는다.

## 5. 변경 규칙

| 변경 | 규칙 |
|---|---|
| 규칙(기간·요일) 수정 | 행은 건드리지 않는다. 예약이 있는 날짜는 V에 남는다. |
| 규칙 삭제/비활성 | 같음. 앞으로 새 날짜가 계산되지 않을 뿐이다. |
| 기본 정원 변경 | **아직 행이 없는 날짜**에만 적용된다. 열린 날짜는 관리자가 날짜별로 바꾼다. |
| 날짜별 정원 변경 | `새 정원 ≥ reserved_seats` 여야 한다. |
| 기본 가격 변경 | 덮어쓰기가 없는 모든 날짜의 신규 예약에 적용. 기존 예약은 단가 스냅샷이라 영향 없음. |
| 출발 취소 (CANCELED) | `reserved_seats = 0` 일 때만 가능. 예약이 있으면 먼저 예약을 취소해야 한다. |
| 마감 (CLOSED) | 신규 예약만 막는다. 기존 예약은 유지. 재개하면 OPEN. |
| 상품 비활성 | 신규 예약만 막는다. 기존 예약·행은 유지. |

## 6. 예약과의 연결

- 예약은 `product_code + departure_date` 를 저장하고, 예약 시점의 상품명·단가를 스냅샷으로 둔다(지금과 같음).
- 좌석 반환(취소·만료)은 같은 `(product, date)` 행의 `reserved_seats` 를 줄인다. 행은 지우지 않는다.

## 7. 정리(선택)

`reserved_seats = 0` 이고 덮어쓰기·`pinned` 가 없는 행은 정보가 없으므로 지워도 되지만, 지우지 않아도 정합성에 영향이 없다. 1단계에서는 정리하지 않는다.

## 8. 관리자 화면

`/admin/products`에서 아래를 관리한다. 모든 쓰기는 `PUT/POST /admin/products/**` (관리자 토큰 필요)를 거치며, 저장 규칙 S2/S3가 그대로 적용된다.

| 탭 | 내용 | 저장 규칙 |
|---|---|---|
| 기본 · 가격 | 상품 코드(등록 후 변경 불가), 이름, 박/일, 기본 정원, 항공·미팅·호텔, 대상 구분별 기본 가격 | `product`, `product_price` 갱신 |
| 일정 | 일차별 항목(항공/관광/식사/호텔/자유). 실제 날짜는 출발일 + 일차 − 1 로 계산 | `product_itinerary` 교체 |
| 출발 규칙 | 규칙(기간 + 요일, 최대 10개)과 제외일(최대 400개) | `departure_rule`, `rule_exclusion` 교체. **`departure` 행은 건드리지 않는다** |
| 출발일 관리 | 계산된 날짜 + 저장된 날짜 달력. 마감/다시 열기, 정원 변경, 출발 취소, 규칙 밖 날짜 추가 | S2/S3: 행을 만들고 `pinned = true` |
| 부가 정보 | 선택관광, 쇼핑, 포함/불포함·유의사항, 조건 | 해당 테이블 교체 |

제약: 정원은 예약 좌석 수 아래로 못 내린다. 출발 취소는 예약이 없을 때만 된다. 상품 비활성화는 새 예약만 막는다.
