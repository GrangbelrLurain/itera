# ADR-001: Go + Rust 분산 구조에서 Java REST + Tauri 얇은 셸로 수렴

| 상태 | 작성일 | 대상 |
| :--- | :--- | :--- |
| Accepted | 2026-11-09 | 코어 트랜잭션 백엔드, 클라이언트 구성 |

## 1. 배경

처음 가설은 Go와 Rust를 쓰는 폴리글랏 분산 구조였다.

```
Client ──(gRPC-Web)──> BFF (Go) ──(gRPC)──> Core engine (Rust) ──> GDS / DB
```

기대한 것은 Rust의 메모리 안전성과 빠른 상태 전이, Go의 가벼운 I/O 게이트웨이, gRPC/Protobuf의 엄격한 스키마였다.

## 2. 문제

1. **병목은 언어가 아니라 데이터베이스다.** 좌석 이중 예약 방지와 취소 정산의 무결성은 트랜잭션 격리 수준과 락 전략에 달려 있다. 코어를 Rust로 분리해도 결국 같은 DB 행 잠금을 기다리므로 언어 성능 이점이 드러나지 않았고, 서비스가 나뉘면서 분산 트랜잭션과 장애 복구만 복잡해졌다.
2. **생태계가 JVM에 몰려 있다.** 항공 GDS와 결제 연동 SDK는 대부분 Java로 제공된다. Rust나 Go에서 쓰려면 FFI나 JNI 래퍼를 직접 만들고 유지해야 하고, 메모리 안전 문제가 다시 생긴다.
3. **gRPC는 브라우저와 맞지 않는다.** 웹과 데스크톱 클라이언트까지 gRPC-Web 프록시가 필요하고, 개발자 도구에서 페이로드를 바로 읽을 수 없어 디버깅과 QA 비용이 늘었다.

## 3. 결정

```
Desktop shell (Tauri v2, Rust)  ──WebView──>  Admin web (Next.js, TypeScript)
                                                    │  REST / JSON, OpenAPI contract
                                                    ▼
                                       Backend API (Java 21, Spring Boot)
```

1. **백엔드는 Java REST 하나로 합친다.** 무결성은 DB 트랜잭션과 서버 쪽 락으로 지키고, 가상 스레드(Java 21)로 블로킹 코드를 그대로 쓰면서 동시성을 확보한다. 리액티브 스택은 쓰지 않는다.
2. **Rust는 데스크톱 셸에 쓴다.** Tauri v2로 시스템 WebView를 감싸고, 창 제어와 파일 저장, 알림 같은 OS 기능만 담당한다. UI는 서버에서 배포되는 웹이 맡으므로 화면 수정에 클라이언트 재배포가 필요 없다.
3. **gRPC 대신 REST + OpenAPI.** 계약(OpenAPI)을 컨트롤러에서 생성해 저장소에 커밋하고, 클라이언트 타입은 그 계약에서 생성한다. 컨트롤러와 계약, 계약과 생성 타입이 어긋나면 테스트가 실패한다.

## 4. 결과

- 한 가지 백엔드 언어와 한 가지 계약 형식으로 줄어, 서비스 간 메시지 정의를 동기화하는 일이 없어졌다.
- 화면은 웹 배포 한 번으로 갱신된다. 셸은 얇아서 바뀔 일이 적다(제목 표시줄처럼 화면에 가까운 것도 웹이 그린다).
- 대가: JVM의 기본 메모리 사용량이 Go나 Rust 서비스보다 크다. 이 프로젝트의 규모에서는 감수할 수 있다고 판단했다.
- 이 문서의 결정은 설계 판단이며 성능 수치로 증명한 것이 아니다. 셸의 크기와 메모리 같은 값은 필요할 때 따로 측정한다.

## 5. 이후 변화

- 관리자 화면은 React + Vite 가 아니라 **Next.js App Router**로 구현했다(서버 컴포넌트와 서버 액션이 백엔드를 호출한다).
- 프런트엔드 패키지 구조와 경계 규칙은 [frontend-architecture](../design/frontend-architecture.md)에 정리했다.
- GDS 연동은 `services/gds-adapter`에 포트-어댑터 구조의 시뮬레이션으로만 있다.
